# Single shared makerspace-card reader for both checkout and return

> **Superseded, 2026-09-16:** [ADR-0005](0005-student-card-registration-and-daily-activation.md) replaces link/return intent with persistent student registration and daily activation. A registered UID no longer means return or unlink. The original reasoning and references to old TODO items below are historical.

One 13.56 MHz makerspace-card reader serves both checkout (link) and return (unlink), replacing the earlier design's two dedicated readers — a link scanner at the dispense box and a separate return scanner at the return drawer. Physically the reader sits at the bottom of an open middle section of the kiosk, so a card can be presented to it from either side. The dispense box and the return drawer remain separate motorised enclosures; only the reader is now shared.

We chose this over two dedicated readers (one per interaction). It is fewer parts, one USB device for the Python core to grab and maintain, simpler wiring, and a single obvious tap point for the student. The trade-off is that the reader no longer encodes *intent*: with two readers the physical location told the kiosk whether a scan meant link or unlink, whereas a single tap is ambiguous on its own.

Intent is therefore derived from the makerspace card's own link state plus session context, not from reader identity and not from a student-card scan at return. A tapped card that is currently **linked** is a return: the kiosk unlinks it and opens the return drawer — no student-card scan required, so a card can be handed back by anyone at any time. A tapped card that is currently **unlinked** depends on context: inside an active checkout session — one a student opened by scanning their student card at the OMNIKEY 5427, which verified training and opened the dispense box — it forms the link; outside any session it is treated as a loose card being handed back, so the return drawer opens for it too, with no link to remove. This means a card that left the pool without ever being linked (the multi-grab / walk-off case in TODO.md) can still be returned. The state machine decides from card state plus session context; the hardware does not.

One consequence: because return needs no student-card scan, the kiosk normally cannot capture *who physically returned* a card (only which student it was linked to). That is consistent with the limited-exposure stance on returns in TODO.md — capturing returner identity would require an optional student-card scan on return, which this flow does not mandate. This supersedes the "both makerspace scanners" framing in ADR-0003; everything else in that ADR (single Python core, output-only scan-driven UI) stands.
